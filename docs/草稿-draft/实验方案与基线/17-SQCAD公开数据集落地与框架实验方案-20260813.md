# SQCAD 公开数据集落地与框架实验方案（2026-08-13）

## 0. 文档定位

理论闭环（Research Gap、T1/T2、P4）已经回答了“为什么持久记忆治理不是普通的分数排序”。本文件回答下一阶段的工程与外部效度问题：把 SQCAD 放到公开长期记忆数据上，在相同候选流、reader、预算和 evaluator 下，与可复现基线比较，并检验理论所预测的失败机制是否在外部数据中出现。

这里必须区分两类证据：

- D0 受控机制世界证明理论机制和下界；
- D1/D2 等公开数据集证明框架在一般任务上的有效性和适用边界。

公开数据集结果不能反过来替代 T1/T2/P4 的证明，也不能仅凭 QA 分数声称“Agent Memory 全领域基础理论”或 SOTA。

## 1. 当前 SQCAD 是否回应 Research Gap

### 1.1 架构层面：符合

SQCAD 的 Evidence–Qualification–Access 分层与已建立的 gap 一一对应：

| 理论要求 | SQCAD 组件 | 可观察对象 |
|---|---|---|
| 记忆不是静态条目，而是会改变未来证据流的持久动作 | Access：keep/downweight/archive/restore/probe | 每个时间点的动作、候选流和后续暴露 |
| 关联或局部效果不能直接授权持久动作 | Evidence 与 Qualification 分离 | evidence、source、scope、version、support、资格状态 |
| 不确定时不能伪装成确定 | Qualification 输出 point/bound/unresolved/mismatch | 置信区间、支持覆盖、冲突和审计原因 |
| 归档可能遮蔽未来纠错证据 | Access 提供付费 probe/restore 通道 | 恢复次数、探测成本、纠错延迟、恢复后证据流 |
| 预算和共记忆造成非可加干扰 | bundle、workspace budget、lineage | bundle-level action、token/latency budget、source-derived lineage |

因此，**设计方向是对的**：它不是单纯把现有检索器换成一个新排序器，而是显式表示“证据—资格—持久访问—未来反馈”的闭环。

### 1.2 实现层面：仍是 prototype，不是完整外部 benchmark 系统

当前 `causal_memory_store.py` 已有 evidence、source、scope、factor、lineage、治理转移、restore 和 decision log；但 `unified_agent_memory_runner.py` 仍主要是一次性排序和固定 retained set 的受控 runner。尚缺：

1. 按时间推进的 persistent archive/restore/probe 动作；
2. 每次动作后重新生成候选流，并记录“被动作改变的未来机会”；
3. LongMemEval/LoCoMo 的统一 reader、答案评估和 chronological future split adapter；
4. 真实 LLM reader 下的 token、延迟和恢复成本记录。

所以目前准确说法是：**SQCAD 架构满足 gap 的机制要求，D0 已验证其理论原型；公开数据集端到端落地尚未完成。**

## 2. 数据集与实验分层

### 2.1 主集：LongMemEval-S（D1）

选择理由：多 session、时间更新、长期事实和跨 session 证据，适合构造 chronological future split 和持久访问干预。当前本地数据已冻结（约 470 个非 abstention 问题、约 18,239 个去重 session），已有 BM25、MiniLM dense、RRF 和 recency/FIFO 结果。

主集先做两个协议：

- **检索协议**：冻结 reader 输入的候选 top-k，测候选是否包含支持证据；
- **端到端 QA 协议**：所有方法使用同一个 reader、同一 prompt、同一上下文 token 上限和同一答案 evaluator。

M split 缺失、模型端点不可用等事实必须在结果表中单列，不能用论文报告数字替代本地复现。

### 2.2 复验集：LoCoMo（D2）

LoCoMo 用于验证 long-horizon multi-hop、temporal QA 和跨 session 更新。先复用 LongMemEval 的 adapter 和 reader，再报告数据许可与预处理版本。它是外部复验，不承担新的理论定理。

### 2.3 第二阶段：MemoryAgentBench / GoodAI-LTM（D3/D4）

用于增量交互、选择性遗忘和持续工作空间压力测试。只有在数据条款、adapter、模型端点和 evaluator 都固定后才进入主表；否则只作为可行性或附录结果。

### 2.4 机制增强集：Gate A + 半合成 chronological overlay（D5/D6）

在公开轨迹上标注或注入 source/derived、scope、版本更新、bundle 和后续纠错事件，形成可审计 packet。注入必须只使用历史时点可见信息，未来答案和纠错标签只用于评估，不能进入治理决策。

## 3. 统一比较协议

所有主表方法共享：

- 同一 chronological candidate stream（按时间切分，禁止未来泄漏）；
- 同一 reader、prompt、context window、retrieval top-k 和 token budget；
- 同一 task/user/tool/model/version 字段；
- 同一答案 evaluator 和随机种子；
- 同一持久动作价格：读 token、写 token、probe、restore、latency 和 workspace 占用；
- 每个方法输出完整 decision log，至少包含 candidate、score/evidence、qualification、action、暴露、答案和未来纠错结果。

比较分三层，避免不可复现的“论文数字拼表”：

1. **R1 可复现控制**：no-memory、keep-all、FIFO/LRU、recency、fixed/frequency decay、BM25、dense、BM25+dense RRF；
2. **R2 结构对照**：association-only、query-local/CMI proxy、item-level causal、bundle-level、no-restore/probe、SQCAD 各消融；
3. **R3 官方系统**：只有 paper、code、data、model、evaluator、protocol 全部核验后纳入；SimpleMem/Oblivion 先固定 commit 和依赖，SAGE、MemAudit、GateMem 等迁移协议未定义时不填主表数字。

## 4. 评价指标

### 4.0 客观性原则：主结果不依赖手工“应保留/应删除”标签

第二层统一合同治理比较的主结果，必须尽量由数据集原生标签、时间顺序和未来真实发生的结果自动计算。否则，如果先由我们人工标注“这条记忆应该保留”，再用该标签评价 SQCAD，就会出现标签定义与方法设计同源、金标泄漏和主观过拟合风险。

因此采用三层证据隔离：

1. **主结果层（objective）**：只使用公开数据集已有答案/支持证据、session 时间戳、后续事实更新、未来问题答案、检索排名、token/延迟/动作日志。`keep/archive/restore` 的好坏由未来 held-out QA、证据召回、时间一致性、成本和未来纠错结果决定，而不是由人工先验标签决定。
2. **机制审计层（diagnostic）**：Gate A 或双人标注只用于划分 scope、source/derived、版本冲突、bundle、纠错和稀有高价值子集，检验理论机制是否被激活。该层不作为总体 SOTA 分数，也不直接训练 SQCAD 的阈值；报告 inter-annotator agreement、标注协议和盲法。
3. **受控因果层（causal validation）**：D0 或公开轨迹上的预注册半合成注入，用已知的 future event 和随机化治理动作定义真值，验证 regret、恢复和探测机制。注入标签来自程序化生成，不是人工判断。

主表应同时给出“全量客观结果”和“机制子集诊断结果”，并明确后者是解释性分层，不是额外金标测试集。

### 4.1 一般性客观指标

- QA：Exact Match、token F1（必要时按 temporal/multi-hop 子类报告）；
- Retrieval：Recall@k、MRR、NDCG；
- temporal consistency：时间更新问题的最新事实准确率、矛盾率；
- multi-hop coverage：支持链完整率；
- 系统成本：输入/输出 token、调用次数、延迟、workspace 占用。

其中 EM/F1、支持证据 Recall、时间一致性和未来纠错成功率来自 held-out 的问题与答案；治理动作的代价由统一合同直接记录。对于没有显式支持证据标签的数据集，只报告答案和检索指标，不把人工补标的“正确记忆集合”冒充原生金标。

这些指标回答“能不能完成任务”，但单独不能证明 self-obscuring 理论。

### 4.2 理论对齐指标

- future utility / lifecycle net benefit；
- false forgetting（误归档导致未来答案损失）；
- harmful retention（保留有害记忆导致未来损失）；
- stale exposure、纠错延迟、evidence-support recovery；
- rare-positive recall（稀有但高价值证据是否被误删）；
- scope transport error、version mismatch rate；
- probe/restore 次数及成本、active token 成本；
- Qualification coverage、unresolved rate、Brier/ECE、coverage–risk 曲线；
- 在注入子集上，按真实未来结局计算 regret，而非用当前 QA 分数反推 regret。

主表必须同时呈现“任务质量—成本”和“未来治理风险”两组指标；不能以 Recall@k 或 EM 单独代替生命周期价值。

## 5. SQCAD 主实验

### 5.1 运行流程

1. 按时间建立 memory state，读取当前时点允许看到的 session；
2. 生成并冻结 candidate stream；
3. 方法输出 Evidence 与 Qualification；
4. 执行 keep/downweight/archive/restore/probe 或 baseline 的等价动作；
5. 在同一 reader 和预算下回答当前任务；
6. 推进到未来 session，记录候选流、纠错机会、答案和成本；
7. 用未来标签计算 QA、检索和 lifecycle 指标。

### 5.2 预注册比较

主比较至少包括：RRF、recency、keep-all、FIFO/LRU、association-only、query-local/CMI proxy、item-level causal、bundle-level control 和 SQCAD。SQCAD 的完整行必须使用动态生命周期 runner；当前 `risk_gated_decomp_abstract` 只能标作受控代理，不能直接等同最终框架。

治理比较的“统一合同”应把每个方法视作一个黑盒 policy：方法只能看到当前时点允许的候选流，统一 runner 负责执行动作、推进时间、调用同一 reader，并自动评估未来结果。这样比较的是 policy 造成的可观测后果，而不是比较各方法自己声称的记忆价值分数。

### 5.3 预期判决

- 在机制激活子集（时间更新、scope 变化、纠错、稀有高价值、候选流受治理动作影响）上，SQCAD 应降低 false forgetting、harmful retention 和 correction latency，并在给定成本合同下提高 net benefit；
- 在普通静态检索子集上，SQCAD 可能与 RRF 持平甚至略差，这是合理边界，不构成理论反例；
- 若总体 QA 不占优，应分别报告质量—成本 Pareto，而不是强行声称 SOTA。

## 6. 消融矩阵

| 消融 | 删除的机制 | 预期现象 |
|---|---|---|
| no qualification | 只按分数直接提交动作 | 自信错误和未来 regret 上升 |
| no scope/version gate | 去掉作用域/版本审查 | transport error、stale exposure 上升 |
| no evidence-silence semantics | 把 archive 后沉默当无证据 | 过度归档，纠错延迟上升 |
| no restore | 禁止恢复通道 | 在 self-obscuring 子集出现线性或明显更高 regret |
| fixed/uncertainty restore | 非 cost-aware 恢复 | 恢复次数或 harmful retention 成本上升 |
| no lineage | source 与 derived 脱钩 | source 删除后无法解释/恢复 derived memory |
| item-level only | 禁止 bundle action | 共同暴露下出现非可加干扰和错误授权 |
| no budget competition | 不让 memory 与 reader 竞争带宽 | 质量提升不能解释真实 token/latency 代价 |
| no positive protection | 去掉稀有高价值保护 | rare-positive recall 下降 |
| no negative attenuation | 不降低有害记忆权重 | harmful retention 上升 |
| no fallback | 不允许 unresolved 时保守访问/探测 | 缺证据条件下错误提交上升 |

每个消融使用同一候选流、reader、预算和 evaluator；至少 10–12 个 seed，报告 paired bootstrap CI，并按机制激活/未激活子集分层。

## 7. 如何解释失败结果

SQCAD 在公开数据上表现不如基线，不会自动推翻理论。需要按层排查：

1. **实现失败**：reader、adapter、预算或候选流不公平；
2. **覆盖不足**：数据集没有 self-obscuring、scope transport 或未来纠错事件；
3. **效用权重不匹配**：SQCAD 优化的 lifecycle net benefit 与 benchmark 的静态 QA 目标不同；
4. **机制假设被反例击穿**：在机制确实激活、协议公平、日志完整且理论预测指标上，SQCAD 仍系统性劣于强基线；此时才需要修改框架或收窄理论量词。

因此，公开 benchmark 的负结果首先是外部效度或目标错配信号；只有在机制激活且理论对齐指标上反复出现反方向证据，才是理论缺口或框架设计本身需要修正。

## 7.1 防止“手工金标过拟合”的审计规则

- 标注者不能看到方法输出、动作结果或测试答案；
- 标注只在开发集完成，测试集的机制分层必须冻结后再揭盲；
- SQCAD 的阈值、候选排序和 restore 规则不能用测试集人工标签调参；
- 任何由人工标注产生的指标，都必须与原生 QA/未来事件指标分栏；
- 若人工机制标签与未来客观结果冲突，主表保留客观结果，并把冲突作为数据/理论边界报告；
- 最终至少报告一个完全不使用 Gate A 标签的结果表，证明优势不是标注闭环造成的。

## 8. 交付门与结论边界

进入“公开数据集主结果”前必须通过：数据 hash、时间切分、candidate stream、reader/evaluator、预算合同、官方基线版本、日志字段和统计脚本冻结。进入“SOTA”表述前还必须满足：至少一个主集和一个复验集、完整端到端 reader、强基线同协议复现、质量与成本同时占优或 Pareto 占优。

当前阶段的正确结论是：**理论核心闭环已完成，SQCAD 架构与 gap 对齐；下一阶段是公开数据集上的外部效度和系统性能验证，而不是继续用普通 QA 分数扩大理论声称。**
