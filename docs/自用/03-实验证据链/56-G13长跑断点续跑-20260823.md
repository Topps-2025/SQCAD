# G-13 具名系统长跑断点续跑（0823）

> **门槛**：G-13（0823 方案 §6.2，Empirics 维度，第 1 批）
> **理由（方案原文）**：`40-` §6 第 2 条：避免事实提取完成后因 embedding/PMI 阶段失败丢失全部工件。成本低，但不做会导致长跑白费。**排在 G-12 之前。**
> **关闭标准**：中断不丢工件。
> **结论**：✅ 关闭。ActMem 与 SimpleMem 两条长跑均已具备**内容寻址断点续跑**，并各自用「模拟中途崩溃 → 重跑」实测验证：崩溃前已付费的生成 100% 复用，只有未完成的部分重新生成。

## 1. 进入本轮时的真实状态（先查，不假设）

`tools/repro_named_actmem.py` **已经有** checkpoint 设施，容易误判为已达标：

| 已有 | 位置 |
|---|---|
| `_atomic_json`（tmp + replace 原子写） | 401 |
| `run_dataset(..., checkpoint: Path \| None = None)` | 428–429 |
| `if checkpoint is not None: _atomic_json(...)` | 465–466 |
| `--checkpoint-dir`（help 写明 "per-trace"） | 513–514 |

但 `grep resume` **零命中**，且写入点在**整条 trace 跑完之后**。也就是说：

- **粒度不对**：一条 trace 内部有 4 个 LLM/GPU 阶段（事实提取 → 因果 → 反事实 → QA）。在 PMI/embedding 阶段炸掉，这条 trace 已付费的全部 LLM 调用被丢弃——正是 G-13 要防的那一条。
- **没有读回**：checkpoint 只写不读，重跑仍从零开始。它是**进度日志**，不是断点。

`tools/repro_named_simplemem.py` 更彻底：`checkpoint|cache|resume` 三个词**零命中**。而 SimpleMem 恰恰是真的因生成预算耗尽而死掉、只剩 `n=1` 冒烟工件的那条（35- / §5.2）。

## 2. 方案：内容寻址缓存，而不是恢复控制流

新增 `src/sqcad/stage_cache.py`（`StageCache`），两条工具共用。

**键 = sha256(model, system, user)**，不是 trace/stage 序号。理由：这些生成在 temperature 0 下是其 prompt 的纯函数，因此内容键在 `--max-traces` 变化、数据集重排、或从不同位置恢复时**依然正确**；序号键在这三种情况下全部失效。

**因此不需要恢复任何控制流状态**：重跑照原路径走一遍，凡是已答过的 prompt 直接从磁盘返回。这比「保存并恢复流水线中间状态」简单得多，也没有状态错位的失败模式。

**持久化 = 只追加 JSONL**，每条 `write` + `flush` + `fsync`。被 kill 造成的**残缺尾行在加载时跳过**（`json.JSONDecodeError` → `continue`），所以中断不可能把缓存本身损坏成不可读。缓存**只存生成**，不是结果工件，永不进入评测器。

**成本口径隔离**（重要，因为 `llm_usage.calls` 在论文里是成本主张）：缓存命中记到 `cache_hits`，**不计入** `calls`/`in_chars`/`out_chars`，且 payload 里带一句 note 说明续跑总数不可与单次跑的成本相比。否则续跑会把成本表做成假账。

## 3. 实测：模拟中途崩溃

不靠推理，直接用假客户端在第 5 个 prompt 抛 `RuntimeError` 打断，然后用同一缓存路径重跑。

| | ActMem | SimpleMem |
|---|---:|---:|
| 首跑真实生成（第 5 个炸） | 4 | 4 |
| 重跑真实生成 | **2** | **2** |
| 重跑 `calls`（成本口径） | 2 | 2 |
| 重跑 `cache_hits` | 4 | 4 |
| 前 4 条输出与首跑逐字一致 | ✅ | ✅ |

即：**6 个 prompt 的任务，崩溃后只补跑剩下的 2 个**，已付费的 4 个不重跑，且成本计数器不被缓存命中污染。

两项额外边界检查：

1. **残缺尾行**：手工往 JSONL 末尾追加半行 JSON，重新加载——跳过该行，其余条目正常命中，不抛异常。**这一条首测失败，是本轮抓到的真 bug**（见 §4.1）。
2. **`response_format` 参与键**（SimpleMem）：同一 messages 但带 `response_format={'type':'json_object'}` 的调用**不会**错命中纯文本缓存（官方 pipeline 的 JSON 模式与文本模式必须区分）。

## 4. 抓到的真 bug：残缺尾行会连带吃掉**下一条**记录

首版实现只在**读**的时候跳过解析失败的尾行，看起来够了。但被 kill 留下的半行**没有换行符结尾**，于是重跑时 append 的第一条新记录直接**拼接**到那半行后面，产生第二条坏行——**崩溃前丢 1 条、崩溃后再丢 1 条**，而且这条是刚刚花钱生成的。这正是 G-13 要防的失败模式，出现在防它的代码里。

修复：加载时检测文件是否以 `\n` 结尾，若不是则在 reopen-for-append 后**先补一个换行**再写。实测已覆盖「同一文件被反复 kill」：连续两次截断后条目数仍为 3 → 4 → 5，无丢失。

教训记录在案：只做「读时容错」不够，**写路径必须修复被破坏的分隔符**，否则容错只保住了旧数据。

## 5. 自查负面 / 边界

- **这不是通用记忆化**：只在 temperature 0 下成立。两条工具都在 wrapper 里**强制** `temperature=0`（SimpleMem 的官方默认是 0.2，wrapper 覆盖为 0），所以前提是代码保证的，不是约定。若日后改为采样解码，缓存必须同时失效——已在 `stage_cache.py` docstring 写明。
- **不防错误结果，只防重复付费**：若首跑的生成本身是坏的（例如解析失败的窗口），缓存会把坏生成也复用。它保的是「不丢工件」，不是「工件正确」。
- **默认关闭**：不传 `--stage-cache` 时 `StageCache(None)` 全程 no-op，冻结合同的既有行为逐位不变。
- **ActMem 仍是 partial**：本轮只解决长跑鲁棒性，**没有**产出 ActMem 的可审计 benchmark trace。§5.2 / Appendix D 的 "paper-mechanism faithful core (partial)" 等级不变，不因本轮而升级。

## 7. 回归测试（补：本轮初版只有临时脚本）

首次自查发现两条工具与 `stage_cache` 在 `tests/` 里**零命中**——即本轮的核心断言只靠一次性脚本支撑，下次改动没有任何东西会拦住 §4 那个 bug 复发。已补 `tests/test_stage_cache.py`（7 项，全绿）：

| 测试 | 断言 |
|---|---|
| `key_is_content_addressed` | 键对 model/system/user 三者均敏感；字段分隔符防边界碰撞（`("m","s","u")` ≠ `("ms","","u")`） |
| `entries_survive_process_restart` | 跨进程持久化命中；hits/misses 计数正确 |
| `truncated_tail_is_skipped_not_resurrected` | 截断尾行不加载，完好条目照常命中 |
| `append_after_truncated_tail_does_not_lose_the_new_record` | **§4 的 bug 专项**：截断后新写入的记录仍可读，坏行恰好 1 条（未吞掉下一条） |
| `repeated_kills_never_lose_a_completed_record` | 连续两轮「截断 → 续写」后，每轮新记录都存活 |
| `hits_and_misses_are_counted_separately` | 命中与未命中分开计数（成本口径隔离的前提） |
| `disabled_cache_is_a_no_op` | `StageCache(None)` 无文件副作用 |

一处需说明的实现事实：修复**不**清除那条已损坏的半行——它的内容不可恢复。修复保证的是它被**限制在一行内**，不再吸收后续追加的记录。测试因此断言「坏行数 == 1」，而不是「全部行可解析」（初版测试断成后者，是测试写错，不是代码错）。
