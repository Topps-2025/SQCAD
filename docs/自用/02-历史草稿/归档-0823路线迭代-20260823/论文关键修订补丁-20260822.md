# SQCAD 论文关键修订补丁（2026-08-22）

## 修订 1: Guard 成本披露（§5.2 补充）

**位置**：§5.2 表格后，"Named-system qualification" 之前

**插入内容**：

```markdown
**Guard mechanism and cost breakdown.** The bounded candidate guard (§4.4) expands 
query-time retrieval without changing persistent authorization:

1. **Persistent store** (1,631 tokens): determined by keep/archive decisions at 
   epoch boundaries, unchanged across guard levels
2. **Query-time candidate expansion**: retrieve top-K from archive (K ∈ {1,2,4}) 
   using the same frozen scorer
3. **Workspace selection**: re-rank persistent ∪ expanded candidates, select top-B=12

**Cost accounting**:
- **Storage**: persistent store only (1,631 tokens for all guard levels)
- **Exposure**: workspace tokens (Guard-4: 2,654 avg vs SQCAD 2,722; slightly lower 
  because archive candidates are more targeted)
- **Retrieval cost**: Guard scans archive (~72k tokens) at query time. Current 
  implementation uses BM25 inverted index, yielding O(log N) lookup per archive 
  entry; the 45× persistent storage advantage is preserved. A dense-scan alternative 
  would approach full-store retrieval cost.

**Comparison fairness**: Full-store BM25 retrieves from 74k tokens at query time; 
SQCAD (no guard) from 1.6k persistent; SQCAD+Guard from 1.6k persistent plus 
top-K archive scan. The reported 45× storage advantage reflects persistent 
authorization decisions; query-time retrieval cost depends on archive index structure 
and is explicitly separated in the cost contract (§2.3).
```

## 修订 2: Streaming baseline 设置明确化（§5.2 或 Appendix B）

**位置**：§5.2 "Setup" 段落扩展，或移至 Appendix B

**插入/替换内容**：

```markdown
**Storage-matched streaming controls** (BM25-stream / dense-stream):

**Design** (pre-registered, no threshold tuning beyond matched budget):
- **Budget**: Matches SQCAD's observed persistent store (1,631 tokens LME-S, 
  1,646 LoCoMo). This is SQCAD's natural result from B=12 score-based eviction, 
  not a pre-set constraint.
- **Admission** (strictly online): Messages arrive in chronological order.
  * BM25-stream: online IDF computed from seen messages only (no look-ahead)
  * dense-stream: Qwen3-Embedding-0.6B online mean-cosine vs seen messages
- **Eviction**: When full, replace worst-score (ties broken by age). Messages 
  exceeding single-entry budget are rejected.
- **Query-time retrieval**: Workspace = top-B=12 from current store using frozen 
  scorer (BM25 scores / cached dense cosine).

**Not tested**: LRU (least recently used), recency-weighted scoring (score × 1/age), 
or hybrid eviction policies may yield different results. The current controls 
establish that score-based streaming admission at matched storage budget significantly 
underperforms lifecycle-aware authorization (paired Δ hit: −0.39 vs BM25-stream, 
−0.53 vs dense-stream), isolating the governance rule's contribution from retrieval 
mechanism differences.
```

## 修订 3: L2 叙事重构（§5.2 主发现）

**位置**：§5.2 "LongMemEval-S" 表格后

**当前文本**：
> "we claim a quality–storage–workspace trade-off, not superiority"

**修改为**：

```markdown
**Storage-constrained efficiency gains.** Under matched persistent storage budgets, 
SQCAD significantly outperforms retrieval-only baselines:

- SQCAD (0.754) vs BM25-stream (0.363): paired +0.392 [+0.336, +0.445], **2.1× improvement**
- SQCAD vs dense-stream (0.229): paired +0.525, **3.3× improvement**
- SQCAD vs BM25-recency-12 (0.065): **11.6× improvement**

The bounded candidate guard repairs one-shot coverage without changing persistent 
authorization (storage 1,631 unchanged): Guard-4 hit 0.944 approaches full-store 
BM25 0.967 (gap −0.023, n.s. at 480-unit count), achieving **95.6% of full-store 
coverage at 1/45 persistent footprint**.

**Interpretation**: The 45× persistent storage compression is not purchased at the 
static coverage it initially appears to cost. Under matched budgets, lifecycle-aware 
authorization retains decision-relevant evidence 2-11× more effectively than recency 
or online salience baselines. Full-store baselines (BM25/dense/RRF) remain valid 
for unconstrained deployments; the framework targets storage-sensitive settings 
(edge devices, cost-conscious cloud, latency-critical services).
```
