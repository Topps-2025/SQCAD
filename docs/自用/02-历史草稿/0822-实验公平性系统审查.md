## 1. L2 实验公平性审查

### 1.1 Storage-matched 对照的设置（B1）

#### **实际设置（来自 34- §5）**

```python
# tools/streaming_managed_baselines.py
预算 = SQCAD 观测存储（冻结工件）
  - LongMemEval-S: 1,631 tokens
  - LoCoMo: 1,646 tokens

准入规则（严格在线，消息按时间序到达）：
  - bm25_stream: 在线 IDF 自信息（idf 由已见消息累积，无 look-ahead）
  - dense_stream: Qwen3-Embedding-0.6B 在线 mean-cos（与已见消息平均余弦）
  
替换策略：
  - 满则替换最差（并列取最旧）
  - 超预算单条不入库
  
任务时检索：
  - workspace = 当前 store 上按冻结 scorer（bm25_scores / 缓存 dense cos）
    做 top-B 检索（B=12）
```

#### **潜在偏差分析**

**问题 1：预算是"观测到的 SQCAD 存储"而非"设计预算"**

| 对比 | SQCAD | BM25-stream |
|---|---|---|
| 预算来源 | 框架运行后观测到的平均存储 | **事后**设置为与 SQCAD 相同 |
| 准入策略 | 评分 + 驱逐（可优化） | 在线 IDF / mean-cos（固定规则） |
| 是否调优 | 未调优（冻结参数） | 未调优（但规则更简单） |

**公平性判断**：
- ✅ **公平的部分**：两者都用相同的 workspace 预算（B=12），相同的检索器（冻结 BM25/dense scorer）
- ⚠️ **有争议的部分**：预算 1,631 是 SQCAD 运行后的观测值，不是预先设定的约束
  - 若 SQCAD 本身就倾向于保留 ~1,600 tokens，那么这个预算可能对 SQCAD 有利
  - 但论文 §5.2 说："SQCAD rows persist at most 12 memories with score-based eviction"
  - 即 SQCAD 的存储是 **12 条记忆的自然结果**，不是为了达到 1,631 而调整

**数据检验**：
```
SQCAD storage (LME-S): 1,631 tokens
BM25-stream storage (LME-S): 1,631 tokens（设计值）

如果 BM25-stream 在 1,631 预算下自然会存储更少（比如 1,200），
那么当前设置可能给了 BM25-stream 更多空间。

但如果 BM25-stream 在 1,631 预算下会尝试存储更多（比如 2,000+），
那么 1,631 的限制对 BM25-stream 是约束。
```

**需要澄清的问题**：
1. SQCAD 的 1,631 是 B=12 的自然结果，还是有其他参数控制？
2. BM25-stream 在没有预算限制时会自然存储多少？
3. 如果 BM25-stream 想存储 3,000+ tokens，那么 1,631 限制是否对其不利？

---

#### **问题 2：在线 IDF vs 离线 IDF**

**BM25-stream 使用"在线 IDF"**：
```python
idf 由已见消息累积，无任何 look-ahead
```

**Full-store BM25 使用"离线 IDF"**：
```
idf 由全部可见历史计算（time-masked，但包含决策点之前的所有消息）
```

**这是否不公平？**

**公平性判断**：
- ✅ **这是公平的**：streaming 的定义就是"只能用已见信息"
- ✅ SQCAD 也是 streaming（决策时只看到 t 之前的消息）
- ✅ Full-store BM25 用离线 IDF 是因为它确实存储了所有历史

**但需要明确披露**：
> "BM25-stream uses online IDF (computed from seen messages only), while 
> full-store BM25 uses offline IDF (computed from all time-masked history). 
> This reflects the information asymmetry inherent to storage-constrained vs 
> full-store settings."

### 1.2 Guard 机制的事后性质（B3，关键）

#### **Guard 是什么**

从论文 §4.4 和表格：
```
SQCAD storage: 1,631, hit: 0.754
SQCAD + Guard-1: 1,631, hit: 0.902
SQCAD + Guard-4: 1,631, hit: 0.944
```

**Guard 机制**：
- 在 SQCAD 的 persistent authorization（keep/archive）之上
- 增加 **bounded candidate expansion**
- 从归档中临时召回 top-K 候选（不改变 persistent store）

#### **潜在偏差：Guard 是"事后修复"**

**问题**：
1. SQCAD 的 persistent authorization 产生了 1,631 tokens storage
2. Guard 在此基础上 **额外** 从 archive 召回候选
3. 但 storage 仍然报告为 1,631（只计算 persistent store）

**这是否公平？**

**关键问题**：Guard 的"临时召回"是否占用了额外的计算/检索资源？

**场景 A：Guard 只是"更宽的检索窗口"**
```python
# SQCAD without Guard
workspace = retrieve_top_B(persistent_store, query, B=12)

# SQCAD with Guard-4
candidates = persistent_store + retrieve_top_4(archive, query)
workspace = retrieve_top_B(candidates, query, B=12)
```

**如果是场景 A**：
- ✅ 公平：Guard 只是"在不改变 persistent 的前提下扩大候选池"
- ✅ Storage 1,631 是正确的（persistent 未变）
- ⚠️ 但需要披露：**检索成本增加**（需要在 archive 上额外检索）

**场景 B：Guard 是"query-time 动态扩展"**
```python
# Guard 在每个 query 时都从整个 archive 检索 top-4
# 相当于 persistent(12) + query-time(4) = 16 条候选
```

**如果是场景 B**：
- ⚠️ 需要明确：这与 "B=12 workspace budget" 的关系
- 如果 baseline 也可以用 B=16，那么对比不公平
- 如果 Guard 的 4 条是 **候选扩展而非 workspace 扩展**，则公平

#### **需要在论文中明确的内容**

```markdown
### Guard mechanism and its cost

The bounded candidate guard (§4.4) expands the retrieval candidate set without 
changing persistent authorization:

1. **Persistent store** (1,631 tokens): determined by keep/archive decisions
2. **Query-time candidate expansion**: retrieve top-K from archive (K ∈ {1,4})
3. **Workspace selection**: re-rank persistent + expanded candidates, select top-B (B=12)

**Cost accounting**:
- Storage: only persistent store (1,631 tokens, unchanged)
- Exposure: workspace tokens (may increase if expanded candidates are selected)
- **Retrieval cost**: Guard requires additional index scan over archive (not counted 
  in current metrics, but proportional to archive size)

**Comparison fairness**: 
- Full-store BM25 retrieves from 74k tokens at query time
- SQCAD retrieves from 1.6k persistent tokens at query time
- SQCAD+Guard retrieves from 1.6k persistent + top-4 archive at query time
- The 45× storage advantage reflects persistent store only; query-time retrieval 
  cost is lower than full-store but higher than SQCAD-only.
```

**这个披露非常重要，否则 reviewer 可能质疑**：
> "You claim 1/45 storage, but Guard actually scans the archive at query time. 
> What is the true retrieval cost?"

### 2.2 Oracle label 的构造（公平性无问题）

**Oracle 定义**（来自 27-）：
```
τ = V(keep) - V(archive)

oracle label:
  keep   if τ > 0.5
  archive if τ < -0.5
  neutral if |τ| ≤ 0.5
```

**公平性判断**：
- ✅ 完全公平：oracle 是"知道完整未来"的真值
- ✅ 所有策略（包括 SQCAD）在决策时 **看不到** oracle label
- ✅ Oracle agreement 是事后评估指标，不是训练目标

### 2.3 Mechanism families 的设计（有轻微耦合）

**当前 6 个 mechanism families**：
1. Rare member (workspace 竞争)
2. Stale threshold (版本过期)
3. Scope mismatch (作用域冲突)
4. Future rescue (恢复价值)
5. Lineage conflict (血缘版本)
6. Self-obscuring (证据删失)

**公平性问题**：
- ⚠️ 这些 mechanism 是根据 SQCAD 的理论（Theorem 1-4）设计的
- 可能存在"理论→实验→验证理论"的循环

**检验**：
- ✅ 如果 mechanism 是从理论**推导**出的，那么验证是公平的
- ❌ 如果 mechanism 是从 SQCAD 实现**观察**到的，那么验证是循环的

**实际情况（从 Theorem 1-4 推断）**：
- Rare member → Theorem 1 的 candidate/workspace access
- Stale/scope → Theorem 4 的 future-lossy
- Self-obscuring → Construction A.1 的 censoring
- **这些是从理论推导到实验，不是循环**

**但需要的泛化测试**：
- 增加 3 个"边界 mechanism"（不在 SQCAD 理论直接预测范围内）
- 验证 interval authorization 是否仍然有效

### 4.2 最关键的问题：Guard 的成本披露

**当前主张**：
> "Guard-4 在 1/45 存储下达到 95.6% 的 full-store 质量"

**潜在 reviewer 质疑**：
> "Storage 1,631 只计算 persistent，但 Guard 在每次 query 时扫描 archive。
> 真实的检索成本是多少？与 full-store 的 74k 相比，是 1/45 还是 1/30？"

**需要补充的分析**：

```markdown
### Guard retrieval cost analysis

**Persistent storage**: 1,631 tokens (45× smaller than full-store 74k)

**Query-time retrieval**:
- Full-store BM25: scan 74,092 tokens → retrieve top-12
- SQCAD (no Guard): scan 1,631 tokens → retrieve top-12
- SQCAD + Guard-4: scan 1,631 (persistent) + retrieve top-4 from archive → re-rank → top-12

**Archive size**: 74,092 - 1,631 = 72,461 tokens

**Guard's additional cost**:
- If archive uses inverted index: ~O(log N) per query → negligible
- If archive uses dense scan: O(72k) per query → similar to full-store
- Current implementation: [需要查看代码确认]

**Conservative estimate**: 
- If Guard scans full archive: effective cost ≈ 1,631 (persistent) + 0.1 × 72,461 (archive scan) 
  ≈ 8,877 tokens equivalent → 8× smaller than full-store (not 45×)
- If Guard uses index: cost ≈ 1,631 + O(log N) → still ~45× advantage

**Recommendation**: Report both persistent storage (1,631) and query-time retrieval 
cost (depends on index structure). Current "45×" claim is valid for persistent 
storage; query-time advantage depends on implementation.
```
