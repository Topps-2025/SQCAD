## 1. 会议结论

本次会议的核心结论是：SQCAD 当前的工作量和研究方向基本没有问题，但需要从“实验和技术路线汇报”收敛为“以论文结果为导向的结构化主线”。论文不能把所有已做内容平铺展示，而应明确哪些是主贡献、哪些是支撑证据、哪些应放入附录或作为后续工作。

建议形成如下论证链：

```text
问题背景与现有工作
    -> research gap 的形式化定义与必要性证明
    -> SQCAD 机制如何针对性补足该 gap
    -> 公开数据集上的任务质量/存储成本权衡
    -> 自建反事实数据集上的生命周期价值验证
    -> 消融、基线、公平性与局限性
    -> 讨论机制为何有效、结论适用到哪里
```

导师认可将 research gap 的证明纳入论文，并建议把证明与方法创新连续组织起来，而不是把理论、框架和实验写成彼此独立的材料堆积。

## 2. 导师对 research gap 与理论部分的判断

### 2.1 research gap 证明应保留

导师明确认为，好的论文不能只依赖实验结果。尤其对于 SQCAD 这种试图重新定义 Agent Memory 持久治理目标的工作，应同时具备：

1. 从逻辑或数学上说明问题确实存在；
2. 说明已有信号或方法为什么不能直接解决该问题；
3. 用实验验证该问题不是纯粹的概念假设；
4. 说明提出的机制如何从理论上补足已证明的缺陷。

因此，当前已有的观测等价、局部因果效应与生命周期价值不一致、作用域迁移限制、self-obscuring 以及 probe/defer 必要性等内容，可以作为论文的理论主线，但需要压缩成少数清晰的命题/定理和反例，不宜把全部研究过程原样放入正文。

### 2.2 理论与方法要形成前后对应

推荐的写法是：

- 先定义持久记忆动作和 lifecycle value，明确本文真正要估计的对象；
- 再证明关联信号、query-local 因果效应或 source-scope 平均不能在一般情况下授权 `keep/archive`；
- 接着提出 SQCAD 的 Evidence–Qualification–Access 分层，以及 probe、restore、candidate guard 等机制；
- 最后用简短证明或机制分析说明这些组件如何对应前面的失败模式。

这里的重点不是声称 C1–C8 是唯一可能的条件，而是说明 SQCAD 提供了一组可操作、可审计的识别与授权路径。

## 3. 对当前实验设计的反馈

### 3.1 公开数据集的作用要收窄

导师认可 LongMemEval-S、LoCoMo 等公开数据集的必要性，但指出它们本身没有同一历史流下的 `keep/archive` 反事实分支，因此不能单独证明记忆生命周期价值或持久动作的因果效果。

公开集更适合回答以下问题：

- 在真实长期轨迹上，任务命中、证据召回和答案质量是否保持在可接受水平；
- SQCAD 是否以更低的 persistent storage 换取有竞争力的 evidence/answer quality；
- candidate guard、probe、restore 等机制是否修复了可定位的 bad case；
- 质量、存储、暴露和探测成本之间是否存在可解释的 Pareto 权衡。

公开集结果不应被写成“SQCAD 全面击败检索基线”或“公开集已经证明 lifecycle causality”。

### 3.2 自建数据集具有必要性，但必须证明不是自娱自乐

导师认为，自建数据集的合理性在于：公开数据没有覆盖本文真正关心的持久治理问题，例如低频高价值记忆、版本更新、有害记忆、归档后的自遮蔽以及未来任务对历史证据的依赖。

但自建数据集要取得可信度，需要同时满足：

1. 清楚说明公开数据为什么无法测量该问题；
2. 公开构造规则、数据生成方式、真值定义和评测器；
3. 使用非 SQCAD 的普通策略、强基线和 oracle/上界进行对比；
4. 做独立实现、未见机制、标签敏感性和防捷径审计；
5. 说明哪些结论只在冻结的规则世界有效，哪些不能外推到真实 Agent Memory；
6. 尽可能加入人类或外部判官锚定，证明标签和场景语义并非完全由作者单方面规定。

因此 LifecycleBench 可以作为论文的重要组成部分，但需要把“为什么必须自建”与“如何防止自建集偏向本文方法”写成数据集设计的一部分，而不是只报告它对 SQCAD 有利的结果。

### 3.3 基线复现要分层处理

导师认可当前对基线开放性和可复现性的分类，但建议采取结果导向的取舍：

- 可完整运行的开源方法：尽量在统一数据、reader、预算和 evaluator 下复现；
- 代码可读但缺少模型、API、依赖或许可证不明确的方法：明确写成官方代码级验证或部分复现；
- 没有官方实现的方法：可以依据论文规则做行为代理，但不能写成官方系统结果；
- 与当前 access-time retention 合同不对应的方法：标记为不可迁移，不要为了凑基线而强行塞入主表。

对于确实无法完整复现的强相关方法，可以引用其论文报告的数字，并明确这是原论文结果；只有在需要把该方法迁移到新数据或新任务时，才必须完成相应的复现闭环。任何情况下都不能把代理数字冒充官方端到端结果。

## 4. 导师对论文主线和贡献的要求

导师认为当前内容很多，但主线和 main contribution 还不够突出。需要从“技术路线图”重新提炼为论文贡献，并明确主次关系。

目前可以考虑的主贡献方向是：

1. **问题/理论贡献：** 将 Agent Memory 的持久治理表述为 lifecycle value 的识别与授权问题，并用构造性理论说明常见关联、局部因果和普通衰减信号的适用边界；
2. **方法贡献：** 提出 Evidence–Qualification–Access 分层，以及资格门控、candidate guard、probe/restore 等针对性机制；
3. **实验/评测贡献：** 建立公开轨迹与反事实 LifecycleBench 的互补评测协议，在任务质量、存储/暴露成本和长期治理风险之间进行联合分析。

需要进一步决定的是：这些内容是否都放在同一篇 ICLR 论文中，还是将理论/治理框架与 benchmark/评测工作拆分为不同论文。导师特别提醒，当前工作量较大，全部塞入一篇文章可能导致主线松散、篇幅超限，也可能浪费后续扩展成期刊论文的空间。

## 5. 推荐的论文结构

导师建议尽快从论文成稿结构出发规划，而不是继续无限扩展实验清单。可采用以下骨架：

### Introduction

- 第一段：Agent Memory 在长期任务中的背景和实际问题；
- 第二段：现有检索、关联、衰减或局部因果方法的共同限制；
- 第三段：明确 persistent `keep/archive` 与 ordinary retrieval 的差别，提出 research gap；
- 第四段：概括 SQCAD 的核心机制、理论结果、公开集结果和 LifecycleBench 结果；
- 最后一段：列出精确、可验证、不过度外推的 contributions。

### Problem Description / Formalization

- 定义 evidence、qualification、access 和 lifecycle value；
- 给出观测合同、动作、未来任务和成本项；
- 用简洁命题/定理说明 gap 的必要性和边界。

### Method

- 解释 SQCAD 如何针对理论失败模式引入机制；
- 描述资格区间、授权、probe/restore、candidate guard 和成本合同；
- 给出必要的算法和复杂度/实现细节。

### Experiments and Results

- L1：理论/机制验证；
- L2：公开数据集上的质量—成本 Pareto；
- L3：LifecycleBench 上的 lifecycle regret、false-commit、safe-commit、abstention 和恢复指标；
- 具名基线按官方复现、验证层、代理和不可迁移分栏；
- 增加机制消融和公平性审计。

### Discussion and Limitations

- 解释哪些机制导致结果改善；
- 讨论公开集与自建集分别能证明什么；
- 说明参数敏感区、scope 前瞻缺口、人类锚定、完整端到端复现等限制；
- 不把低 persistent storage 写成低总成本，不把规则世界结果写成真实部署证明。

### Conclusion

- 回答本文解决的具体问题；
- 总结理论、机制和实验三层结论；
- 明确剩余的 Phase B 和外部效度工作。

## 6. ICLR 投稿与 AI challenge 建议

导师建议从论文规划阶段就按照 ICLR 的评审维度逐条自检，目标不是编造或迎合评分，而是提前暴露 reviewer 可能提出的关键问题。

应重点反复 challenge：

- 新颖性：SQCAD 与现有 causal memory、OPE、selective retention、governance 方法究竟差在哪里；
- 技术正确性：定理假设是否明确，证明是否真的支持主张，哪些只是构造实例；
- 实验严谨性：公开集和自建集的评价目标是否混淆，统计单位和预算是否公平；
- 基线完整性：官方结果、代理结果和不可迁移方法是否清楚分栏；
- 效率与代价：probe、restore、暴露和存储成本是否被同时计入；
- 可复现性：数据、代码、配置、随机种子、评测器和发布包是否完整；
- 表述边界：是否存在“全面 SOTA”“真实因果验证”“自建集代表真实分布”等过度声称。

导师建议使用 AI 作为反复 challenge 和漏洞发现工具，要求 AI 指出具体证据缺口、效率问题、基线问题和可能的低分理由；不能用 AI 捏造实验、引用或结果，也不能把“AI 给出 5 分”当作真实审稿结论。

## 8. 当前未决问题

1. SQCAD 最终是一篇以理论和治理框架为主的 ICLR 论文，还是拆分为方法论文与 benchmark/评测论文；
2. 自建 LifecycleBench 在本篇中承担核心验证还是辅助内部效度验证；
3. 哪些具名基线值得投入端到端复现成本，哪些只保留原论文数字或代理说明；
4. 当前公开集质量—成本 Pareto 是否足以支撑方法贡献，还是需要进一步扩大可复现基线和端到端 reader；
5. Phase B、人类锚定和 scope 前瞻缺口在投稿前需要完成到什么程度；
6. 论文篇幅如何在正文、附录和后续期刊扩展之间分配。

## 9. 本次会议形成的工作原则

- 以最终接收为目标规划论文，但不牺牲事实准确性；
- 先收敛论文主线，再决定哪些实验值得继续做；
- 每个实验都要对应一个明确的论文问题和可验证主张；
- 理论证明、方法机制和实验结果必须前后对应；
- 自建数据集必须公开、可审计、可独立检验，并解释其不可替代性；
- 基线必须标注复现层级，代理不能冒充官方系统；
- 结果写作必须同时呈现收益、代价、失败案例和适用边界；
- 尽快形成初稿，带着完整结构和结果向导师复审，而不是等所有实验都结束后才开始写作。
