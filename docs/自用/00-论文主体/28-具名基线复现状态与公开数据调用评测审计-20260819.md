# 具名基线复现状态与公开数据调用评测审计

> 目的：把“某方法有没有代码”“能不能完整复现”“当前到底有没有进入公开数据主表”三件容易混淆的事分开，并把 LongMemEval-S / LoCoMo 的数据构造、策略调用、评测和统计流程写成可复核的执行说明。
>
> 本文的状态只以本地审计、冻结 commit、代码路径和结果文件为准。`[官方代码]` 表示找到了对应论文身份的官方仓库；`[官方层验证]` 表示只验证了官方代码的一部分；`[代理]` 表示按照论文规则在 SQCAD 统一流上重写了可观测部分；`[不可迁移]` 表示没有定义公平的 access-time 统一合同；`[未复现]` 表示官方端到端仍缺模型、API、依赖、数据或运行闭环。

## 1. 先给结论

### 1.1 “开源”不是一个二元标签

本项目需要使用四级表述：

| 等级 | 实际含义 | 论文中允许的说法 |
|---|---|---|
| A. 官方代码和许可均可获得 | 仓库身份匹配，许可证允许使用/修改，关键数据和入口也可获得 | “官方代码可复现”；若完整依赖、模型和评测也跑通，才可写“端到端复现” |
| B. 代码公开或可读，但端到端资产不齐 | 代码能读或能运行部分模块，但缺 API、模型权重、依赖、数据或闭环 | “官方代码级验证”或“部分复现”；不能写完整系统复现 |
| C. 没有官方实现，只能按论文重写 | 论文给出规则/公式，但找不到可核验的官方仓库或官方数据 | “行为代理”“规则代理”；不能写官方复现 |
| D. 没有可比的统一合同 | 方法是写时门控、事后审计、benchmark 或程序执行闭环，和当前 access-time retention 协议不对应 | “not transportable”；不填主表伪数字 |

因此，“公开可见但要复现”和“完全没有办法获取”要精确说成：

- **公开可见但还没有端到端复现：** SimpleMem、Oblivion、CMI、ActMem；SAGE 代码公开但不属于当前 access-time 合同；
- **官方实现不可获得，只能重写机制：** FadeMem、Memory Worth、DeMem、Trivium、GovMem、ReMe；
- **不是 retention baseline：** GateMem、MemAudit；
- **真正的运行阻塞不完全是 GPU：** SimpleMem/Oblivion/CMI 主要缺 API 或依赖，ActMem 才有明确的 Qwen3-Embedding-8B GPU 门槛。

### 1.2 当前公开数据主表到底跑了谁

`results/public_unified_contract.json` 的修复后主表包含 30 个策略：

- 10 个 R1 简单/检索控制：`no_memory`、`keep_all`、`fifo`、`lru`、`recency`、`fixed_decay`、`frequency_decay`、`bm25`、`dense`、`rrf`；
- 5 个 R2 结构控制：`association_only`、`memory_worth`、`causal_item`、`bundle_control`、`risk_gated_decomp_abstract`；
- 1 个动态 SQCAD 主行；
- 11 个 SQCAD 消融；
- 3 个 Candidate Guard 变体。

这里的 `memory_worth`、`causal_item` 和 `risk_gated_decomp_abstract` 是统一合同中的结构/行为代理，不是相应论文系统的端到端官方实现。FadeMem、Oblivion、DeMem、Trivium、SimpleMem 没有以完整具名系统行进入这张 30 策略主表。

具名方法的补充验证是分开的：

- SimpleMem：`results/simplemem_official_verification.json`，官方 reader + 官方词法评分层的补充行；
- Oblivion：`results/oblivion_official_verification.json`，官方 decay 数学函数的代码级验证；
- LoCoMo 官方 token-F1：`results/locomo_official_qa.json`，对统一合同生成的 30 个策略预测文件统一评分。

## 2. 具名基线开放性与复现状态

### 2.1 官方代码可获得，但完整系统仍需外部资产

#### SimpleMem

- **身份与许可：** `aiming-lab/SimpleMem`，论文 release commit `16912523`，MIT。[官方代码]
- **能拿到什么：** 官方 `test_locomo10.py` 数据读取器、`database/vector_store.py` 词法检索层、LanceDB 相关代码。
- **缺什么：** 论文完整流程还需要 GPT-4.1-mini 生成压缩记忆、Qwen3-Embedding-0.6B 或相应 embedding、LLM answer generation；当前环境没有完整 endpoint/weights 闭环。[未复现]
- **当前验证：** `tools/verify_simplemem_official.py` 原样加载官方 reader，交叉核对 10 个会话、1986 个 QA；将官方 `keyword_search` 规则原样移植到 raw turns，作为 `simplemem_lexical` 补充行。
- **词法规则：** 每个 query keyword 命中 memory 的关键词列表加 2 分，命中 lossless restatement 文本加 1 分，按分数取 `KEYWORD_TOP_K=3`；当前 raw-turn transport 没有官方 LLM 压缩出的 keywords/restatement，所以只是 verified lexical layer。
- **当前补充结果：** Hit=`0.2883`、Recall=`0.2699`、storage=`13,343.8` tokens，10 个 LoCoMo conversation units；这些数字不能称 SimpleMem 完整系统结果。
- **结论：** “MIT 开源、官方读取器和词法层已验证、完整系统未复现”是准确表述。

#### CMI / causal-memory-intervention

- **身份与许可：** `Saksham4796/causal-memory-intervention`，仓库公开，但许可证在当前审计中未核实。[官方代码，license unverified]
- **论文机制：** 对每个候选记忆构造 no-memory、with-memory、perturbed-memory 三种条件，计算当前 query 的局部效用和稳定性，再决定是否保留。
- **能拿到什么：** 官方代码入口、默认 GPT-4o-mini 调用、缓存和 keyless debug fallback。
- **缺什么：** 默认多次 LLM 调用和完整 answer judge；keyless fallback 不是论文端到端实验。[未复现]
- **SQCAD 中的对应行：** `causal_item`。它在公开流上用 query-local observational exposure contrast 估计 `item_effect_lcb`，取 top-12。
- **结论：** 这是“CMI-style local causal proxy”，不能说复现 CMI，也不能把局部 effect 当作 lifecycle action value。

#### ActMem

- **身份与许可：** `nju-websoft/ActMem`，仓库可见，LICENSE 类型未核实。[官方代码，license unverified]
- **论文机制：** 原子事实抽取、聚类、causal-semantic graph、counterfactual retrieval。
- **缺什么：** 事实聚类依赖 Qwen3-Embedding-8B，现实上需要 GPU；DeepSeek-V3/GPT-4o-mini 等层还需要 API。[未复现]
- **当前状态：** 不进入公开数据主表，也没有行为代理数字。
- **结论：** 可以说“公开代码但当前 GPU/API 阻塞”，不能说闭源，也不能说已经比较过 ActMem。

### 2.2 代码可读，但许可证不是开源许可

#### Oblivion

- **身份与许可：** `nec-research/oblivion`，冻结 commit `b2512f9`；代码可读取，但许可证是 NEC Laboratories Europe proprietary，不是 MIT/Apache 类开源许可。[公开可见但非开源]
- **能拿到什么：** decay、Qdrant/RRF 路由、部分 memory activation 代码；本地只在 D 盘数据库原位保存，不随仓库分发。
- **缺什么：** Python `>=3.12` 环境、`qdrant-client` 等依赖、LLM uncertainty/response contribution endpoint；完整系统没有跑通。[未复现]
- **当前验证：** `tools/verify_oblivion_official.py` 逐字执行 `decay_utils.py` 的 `compute_cluster_decay_stats`、`compute_decay_mean`、`compute_decay_variance`，空簇、单分数方差、混合均值/方差断言全部通过。
- **SQCAD 中的关系：** `unified_baseline_runner.py` 有 `oblivion` transported decay-core 规则，但它属于统一合同代理，不是官方端到端行。
- **结论：** 应写“Oblivion 官方 decay 数学代码级验证；完整系统未复现，代码公开但专有许可”，不能写“Oblivion 开源复现”。

### 2.3 没有官方实现，只能做论文规则代理

#### FadeMem

- **官方资产：** 未找到与 Agent Memory 论文身份匹配的官方实现。`aniki-ly/FadeMem` 是视频扩散项目，已按身份冲突排除。
- **论文规则：** 双层记忆、相关性/频率/时间差异衰减、冲突解决、融合和 knapsack pruning。
- **可做的事：** 在统一 candidate stream 上实现差异衰减代理，例如 `$\log(1+freq)\exp(-age/\tau_{sem})$`。
- **不能做的事：** 不能声称 official FadeMem reproduction，也不能把代理的参数说成论文官方参数。

#### Memory Worth

- **官方资产：** 未找到 repository；论文给出了两个计数器和 `hits+/(hits+ + hits-)` 规则。
- **可做的事：** 依据论文规则重写一个关联 success-rate 行；公开集因为真实 success-after-exposure 不能直接观察，使用 query-overlap 事件替代，并明确标 proxy。
- **不能做的事：** 不能把成功率关联信号说成 lifecycle causal value。当前 L3 中 `memory_worth` 与 `storage12` 逐 episode 同动作，是代理退化，不是两篇方法的正式等价。

#### DeMem

- **官方资产：** 未找到与论文身份匹配的官方实现；同名 privacy 项目不算官方代码。
- **论文规则：** 只保留会改变下游决策的 distinction，删除决策中性信息。
- **可做的事：** 用 group effect 与整体均值的差异构造 decision-distinction proxy。
- **不能做的事：** 不能把代理排序当作完整 compression learner/decoder，也不能写官方复现。

#### Trivium

- **官方资产：** 未找到 official repo；论文描述了 causal log、budgeted probes 和 temporal regret。
- **可做的事：** 在统一流上实现 regret-demand/probe layer proxy，用于比较“是否显式付费探测”。
- **不能做的事：** 没有公开 CausalBench-Seq 数据和 70B pilot 闭环，不能填官方数字。

#### GovMem

- **官方资产：** 无 repository；trace 数据和 adjudication labels 为项目内部资产。
- **论文规则：** write-time 的 promote/reject/needs-review，由依赖支持和 counterevidence 驱动。
- **当前状态：** 只能把它作为相关工作和 write-time family 记录；当前 access-time 公开合同没有等价输入，不填主表数字。

#### ReMe

- **官方资产与可比条件：** 当前没有在共享文本流中找到等价的“经验—执行—验证—精炼” agent loop。
- **当前状态：** Phase B 前 `not transportable`，不强行实现一个只保留文本排序的弱代理。

### 2.4 不是 retention baseline，不能硬塞入主表

| 方法 | 它真正是什么 | 为什么不能作为当前公开 retention 行 |
|---|---|---|
| SAGE | Apache-2.0 mem0 fork，write-time novelty gate，Add/Update/Noop | 不在访问时决定 keep/archive；当前合同缺少等价写入事件和 downstream access action |
| GateMem | MIT benchmark，另有 CC-BY-4.0 数据集 | 它是多主体治理评测，不是一个 retention policy；可作为第二阶段 stress test |
| MemAudit | post-hoc poisoned-memory audit 或 package-oracle evaluation protocol | 事后诊断不产生 access-time persistent action；不能与 SQCAD 的 keep/archive 直接比 |

### 3.2 LongMemEval-S：从原始 JSON 到可见 trace

原始样本主要包含 `question_id`、`haystack_session_ids`、`haystack_dates`、`haystack_sessions`、`question`、`question_date`、`question_type` 和 `answer_session_ids`。

`src/sqcad/trace_grounded_runner.py::load_longmemeval_s()` 的构造步骤：

1. 逐个 session、逐个 turn 读取 `role/content`；
2. 将每个 turn 变成 `TraceMsg`，ID 为 `question_id:session_id:turn_index`；
3. 用 `answer_session_ids` 找出 gold 所需 session，并把其中所有 turn ID 收集成 `TraceTask.needed_ids`；
4. 一个 LongMemEval-S sample 当前对应一个 QA task，问题文本转为 `query_tokens`；
5. 每条文本经过 `clean_tokens()`：小写，只保留 `[a-z0-9']+` token；
6. 进入主评估前由 `mask_lme_chronological()` 做时间遮蔽：只保留 `message.date <= question_date` 的消息。

这一步的直觉是：题目在某个历史时点提出，任何策略都只能看到当时已经发生的消息。若 gold needed message 在 question date 之后，它从 Hit/Recall 分母中移除，但策略仍支付它已经暴露的 workspace 成本，避免“不可见真值”被误算成策略漏召回。

### 3.3 LoCoMo：从 session 对话到 QA trace

原始样本包含 `sample_id`、`conversation` 和 `qa`。`conversation` 中的 `session_1`、`session_2` 等列表保存 turn，另有 session date 字段；每个 turn 有 `dia_id`、speaker 和 text。

`src/sqcad/trace_grounded_runner.py::load_locomo()` 的构造步骤：

1. 按 `session_N` 读取所有 turn；
2. 用原始 `dia_id` 作为 `TraceMsg.msg_id`，保留 session、source text、role 和顺序编号；
3. 每条 QA 变成一个 `TraceTask`；问题转为 `query_tokens`，QA 的 `evidence` 中存在于对话的 dia IDs 成为 `needed_ids`；
4. scope 记录为 LoCoMo category；
5. LoCoMo 没有 LongMemEval 那样的逐题 question timestamp，因此当前公开合同把整段 conversation 视为 QA 时已经发生的历史，所有方法按 turn 顺序处理，QA 按冻结文件顺序评估。

这意味着 LoCoMo 适合测试长程证据覆盖和答案质量，但不能单独提供严格的逐题 lifecycle 时间因果。

### 3.4 Loader 构造中的两个重要口径

**LongMemEval 的 session gold 被展开为 turn gold。** 原始文件给的是 `answer_session_ids`，当前 loader 把每个 gold session 中的所有 turn 都加入 `needed_ids`。因此当前 evidence recall 回答的是“gold session 内多少 turn 被 workspace 覆盖”，它比只判断 gold session 是否出现更严格，也不等同于原 benchmark 的最终答案正确率。论文中应称“统一合同 turn-level evidence recall”，不能冒充 LongMemEval 官方 QA 分数。

**LoCoMo 只保留数据中真实存在的 evidence dia IDs。** SimpleMem 官方 reader 统计到 2815 个 evidence IDs，当前合同 loader 过滤不存在于 conversation turn 集合中的 ID 后保留 2806 个；差 9 个 ID。QA 总数 1986 完全一致。这个过滤避免无法匹配的 ID 永远制造 false negative，但必须在复现附录记录，不能写成与官方 reader 的 evidence 列表逐项完全相同。

### 3.5 公开数据不是 LifecycleBench

公开集的 gold 主要是“本题需要哪些 evidence”，而不是“同一状态下 keep 还是 archive 哪个更好”。因此：

- 公开集可以测证据召回、答案 token-F1、旧版本 distractor、存储/暴露成本；
- 公开集不能直接测 `V_keep`、`V_archive`、`tau_keep_archive`；
- chronological overlay 通过程序化注入未来更新、冲突和恢复事件，补充治理目标，但它仍不是原始真实 benchmark 的 lifecycle gold；
- 真正的同源 keep/archive 反事实只能由 LifecycleBench 提供。

## 4. 公开数据策略如何被调用

### 4.1 统一入口和调用顺序

主入口是 `src/sqcad/public_unified_contract.py::main()`。逻辑顺序如下：

```text
读取 JSON
  -> load_longmemeval_s / load_locomo
  -> LongMemEval 做 chronological mask
  -> needed_free：把 gold needed_ids 从策略输入中剥离
  -> trace_features：计算所有共享可观测特征
  -> 对每个 policy 调用 run_policy()
  -> evaluate_trace() 读取 gold 并计算客观指标
  -> aggregate() 按 sample/conversation 聚合
  -> significance() 做配对 bootstrap
  -> 写 results/public_unified_contract.json
```

### 4.2 策略真正拿到的输入

每个策略拿到的是：

- 当前可见的 `TraceMsg`：消息 ID、session、日期、role、content、tokens；
- 当前任务的问题和 `query_tokens`；
- 公共预算 `BUDGET=12`；
- 从可见消息计算的 recency、session frequency、rare session、version overlap、lineage 和 BM25/dense 等信号。

策略拿不到：

- `needed_ids`；
- LongMemEval 的 `answer_session_ids`；
- LoCoMo 的 QA answer 和 evidence；
- 未来被 chronology mask 的消息。

`needed_free()` 会把每个任务的 `needed_ids` 替换为空 tuple；gold 只在 `evaluate_trace()` 和官方 scorer 输入准备阶段出现。

### 4.3 R1 简单和检索控制的调用

| 策略 | 调用规则 | 是否持久治理 |
|---|---|---|
| `no_memory` | 每个任务返回空 workspace | 否 |
| `keep_all` | 所有可见消息都暴露；记录全量 token 成本 | 无治理控制，特意不受 12 条上限约束 |
| `fifo` | 按 `date_idx` 从早到晚排序，取前 12 条 | 静态容量控制 |
| `recency` | 按 `date_idx` 从新到旧排序，取前 12 条 | 静态时间控制 |
| `lru` | 每次 QA 暴露后更新 last-access，再保留最近 12 条 | 动态访问控制 |
| `fixed_decay` | 以统一 half-life 计算 age decay，取 top 12 | 时间衰减 |
| `frequency_decay` | `log1p(session_frequency) * exp(-age/50)`，取 top 12 | 频率加时间衰减 |
| `bm25` | 每个 QA 对全部可见消息做 BM25，取 top 12 | 只检索，不改变持久 store |
| `dense` | 读取 `dense_cache` 中 MiniLM top-12 workspace | 只检索，不改变持久 store |
| `rrf` | 对 BM25 和 dense 名次做 reciprocal-rank fusion，取 top 12 | 只检索，不改变持久 store |

`keep_all` 是“大上下文上限”而非预算内公平策略；BM25/dense/RRF 的 storage 是可见流全量 index token，不能拿它们的高 coverage 直接与 SQCAD 的低 storage 说成同一目标全面胜出。

### 4.4 R2 结构/具名规则代理的调用

#### Association-only

对每条消息计算 `date_idx * log1p(session_frequency)`，静态取 top-12。它是“普通关联信号”的控制，不对应某个完整官方系统。

#### Memory Worth proxy

`_stateful_ratio_engine()` 先遍历 QA 序列。对消息 $m$ 和问题 $q$，若消息 token 与 query token 共享至少 `CONFLICT_OVERLAP=3` 个 token，就记一次 observable hit，否则记一次 failure；最后用 `(hits + 1) / (hits + failures + 2)` 排序取 top-12。

这不是论文中的真实 success-after-exposure，因为公开 QA 流没有把 memory exposure、adoption 和 task success 的因果关系完整记录下来；因此只能叫 Memory Worth proxy。

此外，当前 `_stateful_ratio_engine()` 会先遍历同一 trace 的全部 QA queries，计数完成后才生成一个静态 retained set，并把它用于该 trace 的所有 QA。它不读取 answer/evidence gold，但在 LoCoMo 上使用了完整评测 query 集，属于 transductive proxy，不是严格的逐题 online update。

#### CMI proxy

对每个 QA 先用 BM25 top-12 作为“exposed”集合；对每条消息记录 exposed 和 unexposed 时的 query-overlap value，再以两者均值之差作为 item effect；没有两侧 support 时退回 base score。最终按 effect 静态取 top-12。

这保留了“局部干预效应”这一 estimand 直觉，但没有运行 CMI 官方的三条件 LLM intervention，因此不能写 CMI 端到端复现。

与 Memory Worth proxy 相同，当前实现先遍历整个 QA 序列估计 exposed/unexposed contrast，再为所有任务返回同一静态 top-12。它使用未来 QA query 分布但不使用 gold label。公平表述应是“共享 query 集上的 transductive structural control”；若要作为严格在线基线，需要改为任务 $q_t$ 只使用 $q_1,\ldots,q_{t-1}$ 更新状态，再为 $q_t$ 决策。

#### Bundle control

先计算每条消息的 base score，再按 session 求均值；整组 session 作为竞争单位排序。它测试“把一组相关消息一起治理”是否改变结果。

#### `risk_gated_decomp_abstract`

这是统一合同中的受控 proxy：用可见 conflict gate 代替公开数据不存在的 semantic-confidence/harm-veto 信号，再对冲突消息使用 session mean fallback。它不能代替完整具名方法或动态 SQCAD。

### 4.5 SQCAD 动态行和 Candidate Guard

`run_policy("sqcad", trace)` 调用 `_sqcad_engine()`，分为两个时间层：

**写入/持久层：**

1. 根据 recency、session frequency、rare floor、version conflict bonus 计算 base score；
2. 顺序处理消息，超过 12 条时淘汰最低分；
3. unresolved version pair 不轻易拆分；开启 lineage 时，source 被归档会连带处理 derived orphan；
4. 被淘汰消息进入 archive，保留消息进入 persistent store。

**QA/访问层：**

1. 对当前 query 计算每条消息与问题的 lexical overlap；
2. archive 中与 query 至少共享 3 个 token 的消息最多 probe 1 条；
3. 开启 fallback 时，在 workspace 不满 12 条时从 archive 补入候选；
4. 对 persistent、probe 和 fallback 候选统一做 BM25 排序；冲突消息按 `ATTENUATION=0.8` 降权；
5. probe 条目只有在赢得当前 workspace 的竞争槽位时，才永久 restore；
6. Candidate Guard-1/2/4 在 QA 时额外提出 1、2、4 个 BM25 候选，但这些 candidate 只进入一次性暴露池，不能绕过 Qualification 写入 store。

这解释了为什么 Guard 可以改善公开集 coverage，却不等价于放宽长期授权：它改变的是“当前能否看到候选”，不是“候选是否永久保留”。

## 5. dense 预计算和官方 LoCoMo 评测如何调用

### 5.1 Dense cache

`tools/precompute_dense.py` 在同一 chronology mask 后：

1. 加载 `sentence-transformers/all-MiniLM-L6-v2`；
2. 将每条 visible message 和每个 query 做 mean pooling；
3. 对 embedding 做 L2 normalization；
4. 用 query embedding 与 message embedding 的内积作为 cosine similarity；
5. 每个 task 保存 top-12 message IDs 到 JSON cache；
6. 主 runner 的 `dense` 和 `rrf` 只读取 cache，不在评测循环中偷偷改变模型或候选流。

修复后远端 cache 覆盖 500 个 LongMemEval samples 和 10 个 LoCoMo conversations；`public_unified_contract.py` 没有 cache 时会把 dense/rrf 标记为 skipped，而不是用 BM25 假装补齐。

### 5.2 LoCoMo 预测文件

当主 runner 传入 `--qa-out-dir` 时，`locomo_predictions()` 对每个策略、每个 QA：

1. 取该策略已经选好的 workspace；
2. 在 workspace 内再次用 BM25 取 top-3 turn；
3. 在这 3 个 turn 的句子中，选择与 question token overlap 最大的一句；
4. 把该句作为 `prediction`，把 workspace IDs 作为 `prediction_context`；
5. `write_locomo_qa_files()` 将所有 conversation 累积写成每策略一个 `predictions_<policy>.json`，避免循环覆盖前一个样本。

因此 LoCoMo 当前主结果固定的是同一个 deterministic extractive reader，不是每个基线各自调用不同 LLM。这样隔离的是“记忆选择”差异，而不是模型大小差异。

### 5.3 官方 scorer

`tools/run_locomo_official_scorer.py`：

1. 原样加载冻结的官方 `task_eval/evaluation.py`；
2. 只 stub 未使用的 `bert_score` import，不修改 token-F1 逻辑；
3. 读取每策略 prediction file；
4. 调用 `eval_question_answering(..., eval_key="prediction", metric="f1")`；
5. 输出官方 token-F1 均值、官方 evidence recall 均值、QA 数和 prediction/scorer SHA-256。

当前结果覆盖 `1986 QA × 30 strategies`。LoCoMo token-F1 是确定性文本指标，评测本身不需要 judge LLM；需要外部模型的只是答案生成，而当前合同用固定抽取式 reader 解决了这一层。

### 5.4 LongMemEval 的当前评测边界

LongMemEval 主表目前报告的是 evidence-level Hit、Recall、rare recall、knowledge-update recall、distractor、exposure/storage 等统一合同指标。原 benchmark 的 LLM judge/答案生成层没有被偷偷替换成“官方端到端结果”；当前公开主张应限定为检索覆盖和成本比较。

## 6. Gold 如何隔离，指标如何计算

### 6.1 策略阶段

`needed_free()` 将 `TraceTask.needed_ids` 清空；策略只看到 query 和可见消息。`trace_features()` 计算的 version map、lineage map、rare session 和频率都是从可见消息内容得到的观测特征，不读取 gold evidence。

**但“无 gold 泄漏”不等于“严格在线”。** `memory_worth` 和 `causal_item` 当前会批量读取该 trace 的全部 query 文本来构造静态分数；这属于 future-query leakage / transductive evaluation。BM25/dense/RRF 是按当前 query 即时检索，SQCAD 动态行按冻结 QA 顺序更新；这两类调用语义并不完全相同。现有主表可保留这两行作为结构 proxy，但不应据此做官方系统胜负或严格在线算法比较。

### 6.2 Evaluator 阶段

`evaluate_trace()` 才读取 `t.needed_ids`：

- `hit_rate`：workspace 是否与 needed evidence 有交集；
- `recall_mean`：workspace 找回 needed evidence 的比例；
- `tokens_mean`：实际暴露 token；
- `rare_recall`：rare needed message 是否至少进入一个 workspace；
- `ku_recall/ku_hit`：knowledge-update 子集；
- `distractor_rate`：冲突候选进入 workspace 的比例；
- `storage_tokens`：持久 retained IDs 的 token 总数；
- `lifecycle`：archives/restores/probes/fallbacks 事件计数。

被 chronology mask 完全遮蔽的 needed evidence 不进入 Hit/Recall 目标分母，但仍保留资源成本记录。这样既不惩罚策略无法预知的未来，也不让它免费支付的 workspace 成本消失。

### 6.3 统计阶段

同一个 sample/conversation 对所有策略共享 candidate stream、任务顺序、mask、budget、reader 和 evaluator。`significance()` 用配对 studentized bootstrap：

- LongMemEval：500 sample units；
- LoCoMo：10 conversation units；
- `n_boot=2000`，seed=`20260812`；
- 只要 paired CI 不含 0，才按预注册规则记为显著。

这意味着 LoCoMo 的 1986 QA 是答案评分的粒度，但显著性配对单位仍是 10 个 conversation，而不是把 1986 个 QA 当成完全独立样本。

## 7. 复现路径：什么可以直接跑，什么需要外部条件

### 7.1 当前仓库可直接复核的部分

```powershell
# 公开统一合同：需要 D 盘冻结数据；dense/rrf 需要 dense cache
$env:PYTHONPATH = "src"
python -m sqcad.public_unified_contract `
  --datasets longmemeval_s,locomo `
  --policies no_memory,keep_all,bm25,sqcad,sqcad_candidate_guard_1 `
  --dense-cache remote_results/public_recheck_20260818/dense_cache_all.json `
  --qa-out-dir results/locomo_qa_recheck `
  --output results/public_contract_recheck.json

# LoCoMo 官方 scorer：读取上一步生成的 predictions_*.json
python tools/run_locomo_official_scorer.py `
  --pred-dir results/locomo_qa_recheck `
  --out results/locomo_official_recheck.json
```

若没有 dense cache，`dense`/`rrf` 会被明确标记 `skipped`；若没有 D 盘数据，测试会跳过数据依赖部分，而不是自动下载未知数据。

### 7.2 需要 GPU 或外部模型资产的部分

```powershell
# 生成 dense cache；有 CUDA 时自动使用 GPU
python tools/precompute_dense.py `
  --dataset longmemeval_s `
  --out results/dense_cache_longmemeval_s.json
python tools/precompute_dense.py `
  --dataset locomo `
  --out results/dense_cache_locomo.json
```

这一步依赖 transformers 权重和 `all-MiniLM-L6-v2`；CPU 理论上可运行但 LoCoMo 长对话很慢，远端复现使用 RTX 4080 SUPER 加速。

SimpleMem full、Oblivion full、CMI official 和 ActMem full 还需要各自论文规定的 LLM/embedding/API/依赖，不能用上面的 deterministic reader 或 proxy 行冒充。

## 8. 结果应该怎样写

### 可以写

- “在相同 chronology mask、candidate stream、workspace budget、reader 和 evaluator 下，SQCAD 与 BM25/dense/RRF 进行了统一合同比较。”
- “SimpleMem 的官方 reader 与词法检索层已验证，LLM 压缩/embedding/生成层未复现。”
- “Oblivion 的官方 decay 数学函数已执行并通过语义断言，完整系统受专有许可、环境依赖和 endpoint 阻塞。”
- “FadeMem、Memory Worth、DeMem、Trivium、GovMem 的数字若出现，只能标为论文规则代理。”
- “LoCoMo 官方 token-F1 由冻结 evaluator 统一评分；LongMemEval 当前主表是 evidence-level coverage/cost 结果。”

### 不能写

- “所有具名 SOTA 都已经公平复现”；
- “代码能下载，所以完整系统已经开源复现”；
- “Oblivion 是 MIT/Apache 开源”；
- “Memory Worth/FadeMem/DeMem proxy 数字就是原论文系统数字”；
- “SAGE/GateMem/MemAudit 与 SQCAD 在同一 access-time retention 任务上直接比较”；
- “LoCoMo F1 直接证明 keep/archive 的 lifecycle causal value”；
- “公开主表里的 `risk_gated_decomp_abstract` 就是某个具名系统的官方结果”。
- “公开主表所有策略都严格按相同的 online query-information set 运行”；当前 Memory Worth/CMI proxy 是 transductive 行，需单独标注或后续增加 online 版本。
